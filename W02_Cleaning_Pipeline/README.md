## Purpose and provenance

This workflow cleans and profiles a **seeded synthetic** fleet dataset, not proprietary operational fleet data. It prepares six tables (`sites`, `robots`, `telemetry`, `missions`, `faults`, `maintenance`) for an exploratory data profile and a daily predictive-maintenance modeling frame. Raw inputs are generated by `scripts/generate_fleet.py` and stored in `data/raw/`. The sealed answer key under `data/sealed/` must remain unopened until the scheduled evaluation.

## Cleaning contract

| Topic | Implemented rule | Audit / limitation |
|---|---|---|
| Datetime | Parse documented date/time fields as timezone-aware UTC with errors raised | Invalid timestamps cause pipeline failure |
| Duplicates | Remove **exact duplicate rows** using `drop_duplicates`; one identical copy is retained | Telemetry 109,318 → 109,118 (200 removed); no separate conflict-resolution rule for non-identical duplicate keys |
| Clock drift | Compute median per-robot offset from the nearest 6-hour UTC grid; subtract fixed offset from each robot's telemetry timestamps | Preserve `original_timestamp`; eight robots had nonzero systematic drift (>1 minute), zero after correction; offsets ranged −9 to +20 minutes |
| Outliers | Flag values beyond Q1−1.5×IQR or Q3+1.5×IQR, computed per telemetry column across the cleaned dataset | Keep observations unchanged; 2,906 distinct telemetry rows flagged; IQR is a statistical flag, not proof of sensor error |
| Missingness | Compare cleaned readings with expected six-hour schedule; classify gaps using mission and maintenance overlap | 82 missing scheduled readings: 38 possible connectivity gaps, 44 unknown; unknown **must not** be treated as confirmed robot-off |
| Faults | Use actual `occurred_at`, not delayed logging time, for outcome labels | Severe fault means `severity >= 3` |
| Maintenance | Exclude a robot-day only when maintenance is active **at 00:00 UTC prediction time** | 168 of 27,300 candidate robot-days excluded; later same-day maintenance does not trigger exclusion |

**Important audit detail:** The clock-correction code calculates seconds at whole-second precision; if sub-second drift is introduced in future data, alignment assertions should be extended to nanosecond precision. The current synthetic data passed its assertions.

## Prediction and split contract

Each eligible `(unit_id, date)` is a unique sample. At 00:00 UTC on day **T**, the binary label is 1 if a severity-3-or-higher fault occurs during **[T, T+7 days)**; multiple events still produce one positive label. Historical feature windows end strictly before T (the Week-1 T−1 blackout convention). The last eligible prediction date is **2026-06-24**, ensuring a complete outcome window through 2026-06-30.

Seven-day calendar gaps separate the chronological splits (Nov 1–7 and Mar 1–7). The current builder writes `data/processed/W02_robot_day_modeling_frame.csv`; the internship plan separately requires `data/modelling_frame.parquet`, which **has not been confirmed as created**.

## Known limitations / release checklist

- Synthetic data are for pipeline testing and do not establish real-world fleet failure rates or model performance.
- Outliers are flagged, not removed; missing telemetry is not imputed. A missing reading is not equivalent to a robot being switched off.
- Historical feature coverage: 25,835 of 26,135 robot-days have at least 21 of 28 expected readings in the preceding seven days; 300 have insufficient coverage.
- The current `during_maintenance` column remains `False` on every retained row by construction; it is an exclusion audit indicator, not a predictive feature.
- The pre-fault EDA pooled all splits for descriptive purposes. Week 3 feature selection and threshold tuning should use training/validation only, reserving test for final evaluation.
- Confirm a clean rerun from raw inputs, commit all dependent scripts and a pinned `requirements.txt`, and generate the required Parquet frame and power-check workbook before declaring Week 2 fully submitted.
